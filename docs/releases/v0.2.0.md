# Remanence 0.2.0

## What 0.2.0 is

Remanence 0.2.0, released on 23 November 2026, is alpha software and the first
release with binaries. Do not use it as the only copy of anything. The earlier
v0.1.0 release, on 7 August 2026, published only the conformance test-vector
archive. The withdrawn v1.0.0 release was renumbered to v0.1.0 and remains on
GitHub marked superseded.

0.2.0 is published on [GitHub Releases](https://github.com/archivetechie/remanence/releases/tag/v0.2.0)
with statically linked Linux x86-64 binaries; building from source remains supported.

## What changed since 0.1.0

The [0.2.0 changelog](https://github.com/archivetechie/remanence/blob/v0.2.0/CHANGELOG.md#020--2026-11-23)
lists the changes in full. The main changes are:

- **Generation-2 REM-PARITY tapes.** The terminal index uses three complete
  replicas separated by typed extents. Recovery can use a terminal replica or
  walk from the beginning of tape, and full verification reports damage to
  protected data and parity by address.
- **One standalone drive, no daemon or changer.** `rem setup`, tape
  initialization, put, get, list, finalization and verification work against
  one manually loaded drive. Files are versioned by archive path, unchanged
  versions are skipped, and `rem tape restore` recovers files without the
  original catalog. Start with the [standalone-drive guide](../guide-standalone-drive.md).
- **Write sessions and parity closeout.** Each session owns its parity epoch;
  checkpoints commit objects and clean close writes the remaining sidecar.
  The daemon reconstructs due closeout and finalization work from native logs
  at startup. `rem tape closeout`, catalog tape lists and live status expose
  closeout work and unprotected bytes.
- **Tape checks and confirmation.** Writes and finalization check the tape at
  its recorded end before writing. Re-initializing a cartridge that holds data
  requires typed clobber confirmation, including retired Remanence cartridges.
- **Host authority and rebuild.** Per-tape logs and the library log are the
  rebuild sources for the catalog; audit segments are not. Legacy authority
  is refused, with no importer; see [State from an earlier release](#state-from-an-earlier-release).
- **Restore and verification tools.** Restores retain file modification times
  and stage on the destination filesystem. Full library verification can be
  watched and cancelled. Local recipient-key generation is available through
  `rem archive recipient keygen`.
- **I/O and readiness.** Qualified large objects can stream through an
  overlapping staging ring. Parity encoding selects AVX2, SSSE3 or portable
  routines at runtime. Transfer counts use valid sense data when an adapter
  reports no residual on a check condition. Transient media-readiness and
  changer-not-ready conditions have bounded waits and operator-visible status.
- **Release and dependency checks.** The release workflow builds the binaries
  twice in separate directories and stops if they differ, then checks the
  published release. Dependency updates address the advisories in the changelog.

## Tested on real hardware

On 22 November 2026, after the write-session rewrite, the field-test legs ran on an HPE
MSL3040 LTO-9 partition with one LTO-9 drive and four LTO-9 cartridges. These
were static builds made for the field-test kit from that day's code, rather
than the release archives.

The first attempt that evening was correctly refused at initialization because
the cartridges had been used by other tests. After re-initialization, the rerun
passed every leg:

- Preflight and discovery, then initialization of all four cartridges with
  every beginning-of-tape probe valid.
- Three crash tests: the daemon killed mid-write, an object aborted mid-write,
  and a failed append, each followed by verification of the committed prefix.
- Two full-epoch measurements, one with live control.
- A final pass that waited for media readiness on each cartridge and verified
  every prefix.

After that build, two test-only changes landed, as did a change to tests and
the simulated drive model, power-cut inspection that changes runtime paths,
and release tooling. The field run therefore does not test all runtime paths
in the release archives.

## Known limitations

- **Torn tails after power loss.** When `rem put` is refused at a write-open
  because the tape's recorded end is a torn tail (one possible cause is a power
  cut during a write), the refusal names `rem tape supersede-tail` for the [standalone](../reference-cli.md#rem-tape-supersede-tail-standalone) or
  [library](../reference-cli.md#rem-tape-supersede-tail-library) route.
  On an eligible tail, that command's first run prints its inspection, writes
  nothing to the tape and exits 1, even with confirmation. Other refusals,
  including eligibility checks, automatic finalization failures and a
  confirmation rescan, end without an inspection report. Repair to make such
  a tape writable again is planned for 0.3.0. Other interrupted writes have
  their own recovery rules; start with [`rem doctor`](../reference-cli.md#rem-doctor).
- The published REM-PARITY copy (1.0.0-draft.2) describes generation 1, while
  the in-progress draft covers the generation-2 record layout that 0.2.0 writes
  with three differences found on 23 November; see
  [the REM-PARITY publication copy](../status.md#the-rem-parity-publication-copy).
- Standalone mode has model-backed tests but has not run on a physical
  standalone drive; see [tested hardware](../status.md#tested-hardware).
- [Robot moves wait while a drive becomes ready](../status.md#robot-moves-wait-while-a-drive-becomes-ready),
  even when other bays are idle. A fence requiring release needs operator action.
- [A hard kill during unload can leave a cartridge unthreaded](../status.md#a-cartridge-left-unthreaded-by-a-hard-kill).
  After a hard kill, check `rem top` and `rem tape quarantine list`.
- The [catalog rebuild summary](../status.md#catalog-rebuild-reads-the-library-log-and-the-tape-logs)
  prints `audit records: 0` and a `tape logs:` count that repeats the catalog's tape count.
- Earlier October field testing measured writes at about 190 MB/s on LTO-9
  drives rated at 300 MB/s; the [status page](../status.md#write-throughput-is-below-the-drive-rate)
  records the host's 1 MiB command limit and small number of commands in flight.
- [Two tests are timing-sensitive](../status.md#two-tests-are-timing-sensitive).

## State from an earlier release

0.2.0 refuses tapes written by 0.1.0, whose REM-PARITY bootstrap uses
`schema_major = 1`, and state directories that predate the tape-log format.
Keep any state directory that 0.2.0 opens. Read the refusal first: the
legacy-authority refusal contains
`This state directory predates the current tape-log format` after an
`invalid config: ` prefix. A refusal about the catalog's schema version is a
different case: do not reset for it; keep the directory and
[report it](https://github.com/archivetechie/remanence/issues).
On a legacy-authority refusal, stop the daemon, preserve the records and follow the
[declared-reset procedure](../guide-troubleshooting.md#authority-layout-refusals-and-declared-reset).
A declared reset archives the host's authority and imports nothing.
Re-initialize only tapes whose contents you hold elsewhere.

## Downloads and verification

The main archive, `remanence-0.2.0-x86_64-unknown-linux-musl.tar.gz`, contains
`bin/rem`, `bin/rem-debug`, `bin/rem-daemon` and `bin/rem-recover`, plus
`README.md`, `LICENSING.md`, `LICENSE-APACHE-2.0`, `THIRD-PARTY-LICENSES.html`
and `docs/`. The release also publishes `rem-recover-x86_64-linux-musl.tar.gz`,
`SHA256SUMS`, `release-manifest.json`, `build-remanence-linux.json`,
`eligibility.json` and `THIRD-PARTY-LICENSES.html`, with GitHub attestations of
the checksum-listed files.

[Installing Remanence](../guide-install.md) covers downloading and installing
the archive or building from source. [Release verification](../guide-release-verification.md)
explains how to check the downloads.
