# Remanence 0.2.1 (draft release note)

> This is a draft. The version number and date are not final, and the
> statements listed under [Before publication](#before-publication) have not
> been confirmed.

Remanence 0.2.1 is an alpha release. Its main addition is direct operation of
one standalone LTO drive, with no daemon and no changer. It also makes every
tape write check the tape itself before the first block, requires a typed
confirmation before a cartridge that holds data is re-initialized, and reads
the transferred byte count correctly on hosts whose adapters report no
residual. The format specifications and their test vectors are unchanged. As
before, do not make Remanence the only copy of anything.

[CHANGELOG.md](../../CHANGELOG.md) lists every change. This note covers what an
operator will notice, what was tested on real hardware, what is known not to
work, and how to upgrade.

## What changed since 0.2.0

- **One standalone drive, no daemon.** `rem setup`, `rem tape init`,
  `rem put`, `rem list`, `rem get`, `rem tape finalize` and `rem tape verify`
  work against one manually loaded drive, with state kept under
  `${XDG_STATE_HOME:-$HOME/.local/state}/rem`. Files are versioned by archive
  path, and a file whose newest stored version is unchanged is not written
  again. `rem tape restore` recovers files from a tape without the original
  catalog. The [standalone-drive guide](../guide-standalone-drive.md) is the
  place to start. This path has not yet run on a physical standalone drive.
- **Every write checks the tape first.** Before the first block of a write or
  a finalization, through the daemon or standalone, the tape is read at its
  recorded end. Data there that local state does not account for refuses the
  write with `TailBeyondKnownState`. `rem tape supersede-tail` is the explicit,
  confirmed way to discard such data, after rescuing what is needed.
- **Re-initializing a cartridge that holds data needs a typed confirmation.**
  This includes a retired Remanence cartridge that still carries its old data,
  which 0.2.0 re-initialized without asking. Pass
  `--clobber-data --confirm-clobber "CLOBBER <label>"`, or type or pipe the
  same text. A partitioned cartridge, such as one formatted for LTFS, is
  refused with the command that makes it single-partition.
- **Restores keep file modification times** and stage on the destination
  filesystem, not in `$TMPDIR`.
- **Recipient keys can be generated locally** with
  `rem archive recipient keygen`.
- **Reads continue under a low memory-lock limit**, with unlocked buffers and
  a single warning. `rem doctor` reports the limit.
- **Hosts whose adapters report no residual on a check condition** recognize
  physical end of data. The field-test host is one of them. Programs that use
  `remanence-library` directly must accept the new
  `TapeIoError::CheckConditionWithResidue` variant.
- **Overlap-mode writes** to a newly initialized tape succeed from the first
  object.
- **Layer 5 API.** A `SupersedeTail` RPC, endpoint information in the health
  and version responses, an optional `mtime` on file records and appends, and
  `CartridgeFacts.cartridge_generation` as an optional field that is absent
  when the generation is unknown.
- **Security updates** to `rustls`, `rustls-webpki` and `ctutils` for the
  advisories named in the changelog.

## Tested on real hardware

On 26 and 27 October 2026 the library paths ran on an HPE MSL3040, in its
LTO-9 partition, with three LTO-9 drives and four new LTO-9 cartridges. The
binaries were static builds made for the field-test kit from commit
`9efe1122`, not the release archives. Later commits change tests,
documentation, the wording of one error message and the field-test kit.

These passed:

- Discovery, daemon start, and initialization of all four cartridges.
- A 4 GiB plaintext object written and read back with a matching SHA-256, and
  a ranged read from it. An encrypted object sealed to a primary and a
  recovery recipient, written and read back.
- Multi-object writes, and the append loop in session mode and in cycle mode.
- Write and read benchmarks, and a restore running beside an append on another
  pool.
- Drive stewardship, the TapeAlert probe, a robotic slot-to-slot move and a
  cleaning cycle.
- Recovery. The daemon was killed in the middle of an append; the committed
  object read back intact and the next write succeeded. A plain
  re-initialization of a written tape was refused. A cartridge was retired and
  re-initialized through the confirmed clobber route, and after a restart the
  catalog showed its new identity. The catalog was rebuilt from the audit log
  and journals, and an object written before the rebuild read back intact.
- The plaintext and encrypted write-and-read test again, after the fault tests.
- An overnight soak, stopped early to limit drive wear. On one pool, 335
  write-and-verify cycles completed with no read failures and no mismatches;
  three writes failed while a drive was stalled (see below). On the other pool,
  94 cycles wrote 372 objects with no mismatches and one failed cycle.
- Read-only diagnostics captures with the drives empty, with cartridges
  seated, and after the soak.

This window did not cover parity-protected tapes or a physical standalone
drive. Concurrent write sessions were tried and failed, as described next.

## Known limitations

[What works, and what does not](../status.md) describes each of these in more
detail.

- On a library with several drives, the daemon gives a second concurrent write
  session an idle drive, but while any drive has a media-readiness fence it
  refuses every request in that library that needs the robot, and the clients'
  resume calls then find the fenced drive busy. Open write sessions one at a
  time.
- When a drive holds a cartridge it has not threaded and asks for an
  initializing command, the daemon's media-readiness check polls it instead of
  sending a LOAD, and writes wait on the resulting `media_initializing` fence.
  A LOAD sent by hand (the field window used `sg_start --load` on the drive's
  sg node) clears it at the next poll.
- A daemon killed outright while unloading a cartridge can leave the cartridge
  unthreaded in the drive, which leads to the stall above. Let the daemon exit
  on its own after a stop signal. After any hard kill, check `rem top` and
  `rem tape quarantine list`.
- The summary printed by `rem rebuild-catalog-from-journals` has no line for
  the checkpoint journals it replays, so its counts can read zero after a
  rebuild that restored a complete catalog.
- On the field-test host, writes ran at about 190 MB/s on LTO-9 drives rated
  at 300 MB/s. The host adapter limits each SCSI command to 1 MiB, and the
  daemon's staging ring keeps only a few such commands in flight.
- Two tests fail intermittently on timing; they are named on the status page.

Two operating notes came out of the same window. The first load of a new
LTO-9 cartridge includes the drive's media calibration, which took about 40
to 70 minutes per cartridge, and initialization waits for it. Put new
cartridges only into empty slots that are not the home slot of a cartridge
currently in a drive; otherwise that cartridge cannot return home, and the
fence left behind blocks the next initialization until the cartridge is moved
and the fence is released with `rem tape quarantine release`.

## Upgrading from 0.2.0

The catalog schema moves from 18 to 20. The change adds an index on file paths
and is made in place.

1. Stop the daemon and let it exit on its own.
2. Back up the whole state directory, including the journal, audit and catalog
   paths if your configuration places them elsewhere. A 0.2.0 binary refuses
   the upgraded catalog, so this backup is the way back.
3. Install the new binaries. Replacing a binary drops its file capabilities;
   grant `CAP_SYS_RAWIO` again as the [quickstart](../guide-quickstart.md)
   describes, or in the systemd unit.
4. Start the daemon. Opening the state for writing migrates the catalog to
   schema 20. Until that has happened, commands that only read the catalog
   refuse it with a message that it "predates the unsigned structural-index
   schema 20". Among them are `rem list`, `rem doctor`, `rem drives`,
   `rem tape quarantine list` and the `--dry-run` forms of `rem tape init` and
   `rem tape retire`. That message does not mean the catalog must be rebuilt.
5. Update scripts that re-initialize retired cartridges to pass
   `--clobber-data --confirm-clobber "CLOBBER <label>"`. A library
   `rem tape init --clobber-data` that receives no confirmation is refused with
   a message naming that flag.
6. API clients should treat an absent `CartridgeFacts.cartridge_generation` as
   unknown.

Going back to 0.2.0 means restoring the backup from step 2 with the 0.2.0
binaries. Do not do that if any tape was written after the upgrade: 0.2.0 does
not check the tape before appending, so with the older state it can overwrite
objects written after the backup was taken.

## Upgrading from a state directory older than 0.2.0

Read the 0.2.0 entry in the changelog first. Tapes written by 0.1.0 use the
earlier REM-PARITY layout (`schema_major = 1`) and cannot be read by this
release, and checkpoint files of format version 2 are refused, so a state
directory from 0.1.0 or earlier needs a clean slate for new work.

To keep the old catalog's history for reference, rebuild it. A catalog older
than schema 16 is refused at startup, and `rem rebuild-catalog-from-journals`
refuses it too, because the rebuild opens the existing catalog before it
replays anything. Stop the daemon, move the file named by `index.sqlite_path`
aside without deleting it, and run
`rem rebuild-catalog-from-journals --config <PATH>`. The command, as the
[CLI reference](../reference-cli.md#catalog-rebuild) describes, rebuilds the
catalog from the audit log and the journals, and here it creates a new
schema-20 catalog. This was done once in the field window, on a state
directory from a July 2026 build; the rebuild completed with audit-replay
divergence warnings. A rebuilt catalog does not make tapes in the earlier
layout readable.

## Downloads and verification

The binaries are statically linked against musl and ship in one archive,
`remanence-<version>-x86_64-unknown-linux-musl.tar.gz`, which holds `rem`,
`rem-debug`, `rem-daemon` and `rem-recover` under `bin/` with the README, the
licensing files and `docs/`. It replaces `remanence-x86_64-linux.tar.gz`. The
release also carries `rem-recover-x86_64-linux-musl.tar.gz`, `SHA256SUMS`,
`release-manifest.json`, `build-remanence-linux.json`, `eligibility.json` and
`THIRD-PARTY-LICENSES.html`, with a GitHub build attestation.

Before it publishes, the release workflow runs `cargo fmt`, `cargo clippy` and
`cargo test`, checks the files against `SHA256SUMS` on a clean runner, and runs
each binary in an otherwise empty root, where `rem`, `rem-debug` and
`rem-daemon` must print the tag's version with `--version`. A manual run of the
workflow builds and verifies the same files as a preview and publishes nothing.
[Installing Remanence](../guide-install.md) covers downloading and installing
the archive, and [release verification](../guide-release-verification.md)
explains how to check the files.

## Before publication

These statements could not be confirmed when this draft was written.

- The write throughput figure of about 190 MB/s and its cause come from the
  field window's morning throughput run, whose results are not in the notes
  this draft was checked against.
- Whether parity-protected tapes were exercised by hand at the end of the
  window. The notes end before that work.
- The read-only refusal in upgrade step 4 comes from reading the code. It has
  not been run against a real 0.2.0 state directory.
- Whether `rem rebuild-catalog-from-journals` accepts a state directory that
  still holds checkpoint files of format version 2.
- Whether rebuilding a schema-20 catalog with 0.2.0 binaries, instead of
  restoring a backup, is a safe way back. It is not recommended above.
- Whether letting the daemon exit on its own avoids the unthreaded cartridge.
  The field stop script killed the daemon shortly after asking it to stop; a
  longer wait has not been tested.
- The privileges `sg_start --load` needs on a host where the account lacks
  `CAP_SYS_RAWIO`.
- Whether the version should be 0.3.0. The new `TapeIoError` variant is a
  breaking change for programs that match the enum exhaustively, and the
  catalog migration cannot be reversed by a 0.2.0 binary.
