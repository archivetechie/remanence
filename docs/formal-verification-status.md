# Formal verification status

This document is the reviewer-facing inventory for Remanence formal proof work.
The detailed theorem statements live in each `verif/*/SPEC.md`; this page says
what is proved, what is only tied by drift guards, and what remains normal Rust
test coverage.

The proofs cover the CRC public slice loop, the REM-OBJECT manifest array/fold
and membership bridge, the parity sidecar layout and range bridge, and the
terminal-suffix capacity and pool-admission kernels. Each is a small piece of
arithmetic or decision logic, proved in the Lean theorem prover over a
proof-facing extraction of the production code.

## Trust model

The trust anchor for local proof claims is the Lean type checker accepting the
project with no local `sorry`, `axiom`, or `admit` in the target proof files.
Automated proof-search and editing tools are aids only; they are not part of
the trusted proof base.

Each proof area has two layers:

- A proof-facing Rust extraction in `verif/<area>/src/lib.rs`.
- A Lean proof over Aeneas-generated definitions plus hand-written
  specification theorems in `verif/<area>/lean`.

Every extraction crate has a Rust `drift_guard` test. That test pins
selected production snippets and selected extraction snippets. It is a useful
change detector, but it is not a semantic proof that the extraction and
production code are identical. The capacity and pool-admission extractions
additionally add compiled-production behavioral matrices. Separately, the
inventory freshly regenerates the Aeneas output for capacity, sidecar-layout,
and pool-admission and compares it byte-for-byte with the checked-in Lean
definitions.

Current Lean builds replay external Aeneas files that warn about `sorry` in
`Aeneas.Std.Slice` and `Aeneas.Std.StringIter`. The local Remanence proof files
listed below are expected to have no local placeholders.

## Normal-test-only areas

These are intentionally outside the current formal proof surface:

- SCSI/changer/drive behavior and all physical tape interactions.
- Layer-5 daemon session orchestration, cancellation, concurrency, and gRPC.
- SQLite catalog persistence and rebuild paths.
- REM-OBJECT header/key-frame/prefix geometry and archive composition beyond the
  metadata and manifest proof surfaces.
- Production sidecar byte-buffer construction/parsing beyond the proved fixed
  scalar layout, CRC-window, and range-bound arithmetic.
- Terminal replica and separation byte codecs, actual five-component
  barrier/journal progress, EOD positioning, byte-level survivor agreement,
  and the physical all-invalid BOT recovery walk. Their scalar capacity and
  compact decision invariants are proved; their media behavior is normal Rust
  and scenario coverage.
- AEAD cryptographic security and keyed authentication.
- REM-OBJECT key-frame geometry and header/key-frame codec proofs, tracked as
  **REM-OBJECT-FORMAL-PREFIX** and **REM-OBJECT-FORMAL-HEADER-KEY-FRAME**.
- End-to-end write/read/verify scenarios in the sibling integration harness.

Those areas remain covered by Rust unit tests, integration tests, system
scenarios, code review, and operational runbooks.

## How to check the proof inventory

For a full local proof refresh, run the inventory gate:

```text
make proof-inventory
```

This discovers each proof crate and runs:

```text
fresh Charon+Aeneas generated-Lean comparison
cargo test drift_guard -- --list
cargo test drift_guard
cargo test
lake build
maintained Lean placeholder scan
```

The current proof areas are:

```text
crc64-xz
parity-capacity
parity-sidecar-layout
parity-mapping
parity-state
pool-selection
rem-object-manifest
rem-object-metadata
tape-init
```

Repo-level gates still matter even for proof-only/doc-only edits:

```text
cargo test
cargo fmt --check
cargo clippy -- -D warnings
cargo build --release
```

## Practical wording

Use this wording in comments and design docs:

```text
This pure arithmetic/decision kernel has a Lean proof in verif/<area>; see
docs/formal-verification-status.md and verif/<area>/SPEC.md for scope.
```

Avoid this wording:

```text
This code is formally proved correct.
```

The second sentence overclaims. The current proofs cover specific kernels under specific extraction and scope boundaries.

## Not yet proved

There is no live formal claim for REM-OBJECT header, prefix geometry,
key-frame dependent range geometry, the scalar-header and key-frame codec, or
archive-level composition. These are tracked as **REM-OBJECT-FORMAL-PREFIX**
and **REM-OBJECT-FORMAL-HEADER-KEY-FRAME**, and proofs for them start from
fresh extractions of the encrypted-representation code. The metadata and
manifest proofs above cover only the writer-schema pieces listed in the table.

## Limits of the schema-number proofs

The writer-schema numbers in the rem-object-manifest and rem-object-metadata
proofs (map lengths, version values, digest byte length, entry counts) are
proved equal to the extracted module constants, not to independent literals. If
a constant were extracted wrongly, the round trips would move with it. The
drift-guard tests that pin the production source anchor those numbers, and that
is the intended division of labor. The tape-init proof covers the enumerated
decision tuples, as point-checks, not a quantified decision-table invariant.
