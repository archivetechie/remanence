# Formal verification status

This page is for a reviewer who wants to know which parts of Remanence carry a
machine-checked proof, what each proof states, and what it leaves out. It
covers the nine proof areas under `verif/`. The exact theorem statements are
in each area's `verif/<area>/SPEC.md`, and `verif/STATUS.md` is the short index
kept beside the proofs.

Every proof here is about a small piece of arithmetic or decision logic: a
CRC (cyclic redundancy check), a parity coordinate mapping, a byte layout, a
capacity calculation, a ranking rule, or the decision table that `tape init`
follows. None of them is
a proof about tape input and output, the daemon, the catalog, or cryptography.

## How a proof is built

Each area has three parts.

1. An extraction: a separate Rust crate in `verif/<area>/src/lib.rs` that
   restates the production function in a form the tools can translate. Some
   extractions copy the production code line for line. Others replace values
   that do not affect the logic with small stand-ins: a UUID becomes an
   integer that is only compared for equality, and a SHA-256 digest becomes
   four opaque 64-bit words.
2. Generated Lean definitions. Charon compiles the extraction crate into
   LLBC, the input language of Aeneas, and Aeneas translates LLBC into Lean 4
   definitions. The results are `verif/<area>/lean/<Name>/Funs.lean` and, in
   five areas, `Types.lean`. Each file starts with
   `THIS FILE WAS AUTOMATICALLY GENERATED BY AENEAS`.
3. Hand-written theorems in `verif/<area>/lean/<Name>/Spec.lean`, which state
   properties of the generated definitions. Lean 4 checks them when
   `lake build` runs in `verif/<area>/lean`. Every area pins the toolchain
   `leanprover/lean4:v4.30.0-rc2` in its `lean-toolchain` file.

A drift guard ties the extraction back to the production source. It is a Rust
test named `drift_guard` in each extraction crate. It reads the production
file and checks that chosen lines still appear in it word for word, and it
checks that the extraction still contains its own counterparts of those
lines. The parity-capacity guard also checks whole regions of production
source by length and fingerprint. A drift guard is a change detector: it fails
when a pinned line changes, and it says nothing about code it does not pin.

Two areas compare behaviour as well as text. The parity-capacity and
pool-selection test crates compile the production functions into the test and
compare their results with the extraction's across boundary and overflow
inputs.

## What a passing proof establishes

A theorem that Lean accepts holds for the generated Lean definitions. The
inventory gate (below) also checks that no project Lean file contains `sorry`,
`admit` or `axiom`, the three ways a Lean file can skip a proof or assume a
fact. How a proof was found does not matter: the checker's acceptance is the
only evidence.

The step from that theorem to the code that runs rests on three links, and
each is checked in a different way.

| Link | How it is checked | Remarks |
| --- | --- | --- |
| Generated Lean matches the extraction | Aeneas's translation is trusted. For parity-capacity, parity-sidecar-layout and pool-selection, the inventory regenerates the Lean in a temporary directory and compares it byte for byte with the checked-in files. | The other six areas' generated files are not regenerated by the gate. |
| The extraction matches production | The drift guard, and in two areas the compiled behaviour comparison. | A text comparison of pinned lines is not a proof that the two functions are equal. |
| The Lean libraries the proofs build on are sound | Not checked by the gate. | The Aeneas Lean library contains `sorry` in `Aeneas.Std.Slice` and `Aeneas.Std.StringIter`, and `lake build` reports them as warnings. The placeholder scan covers only the project's own files. In Aeneas revision `45061fa1` the placeholders are in `core.slice.Slice.get_unchecked`, a lemma about it, and `core.str.iter.IteratorChars.collect`; no project Lean file refers to them. |

## The proved areas

Each entry names the production target, what the Lean theorems prove about
the extraction, and what they leave out. The area's `SPEC.md` has the exact
statements.

### crc64-xz

Target: `crates/remanence-crc/src/lib.rs`, the CRC-64/XZ used by parity
sidecars and the audit log.

The proofs show that the extracted bit step, byte-table entry, one-byte table
update and whole-slice loop each return exactly the bit-vector definition of
CRC-64/XZ, for every input. The Rust tests check the specification's six
CRC vectors, such as `crc64("123456789") = 0x995DC9BBDF1939FA`.

Not proved: which bytes a caller passes to the CRC, and (see the status above)
the eight-bytes-at-a-time loop that production now uses for whole slices.

### parity-mapping

Target: the arithmetic in `crates/remanence-parity/src/mapping.rs` that places
data blocks in a parity epoch. A parity epoch is a group of data blocks
protected together by one sidecar; it holds `S` stripes of `k` data blocks
each (see [epoch](reference-glossary.md#epoch-parity-epoch)).

The proofs cover the epoch size `S × k`, that every coordinate produced is in
bounds, the row-major shape of the mapping, the round trip from ordinal to
coordinate and back, and the refusal of parity coordinates and out-of-range
coordinates.

Not proved: sidecar encoding and tape input and output.

### parity-state

Target: `ObjectParityState` and `ObjectParityStateUpdateRange` in
`crates/remanence-parity/src/model.rs`, which classify an object as pending,
partially protected or protected. Each data block has an ordinal, its
position in the tape's sequence of data blocks, and the parity watermark is
the ordinal below which written sidecars cover the data.

The proofs cover:

- the classification itself, for every nonempty block range that does not
  overflow;
- that classification fails exactly when the block count is zero or the range
  overflows;
- that an object the recompute predicate skips cannot have changed state when
  the watermark advances, so skipping it is safe;
- that protection never regresses as the watermark rises;
- that the convenience wrapper agrees with the primitive definitions.

Not proved: when the daemon recomputes, how the catalog stores the result, and
any reconstruction of data from parity.

### parity-sidecar-layout

Target: the fixed-layout arithmetic in `crates/remanence-parity/src/sidecar.rs`.
A sidecar is the tape file that holds an epoch's parity.

The proofs cover:

- the fixed byte ranges of the sidecar header and footer;
- the bytes each header and footer CRC covers, and where each CRC is stored;
- the trailing CRC ranges of block 0 and of the spill-index blocks;
- the block placement of a whole sidecar tape file: header copy, parity
  blocks, tail copy and footer, `2H + P + 1` blocks in all;
- the refusal of blocks that are too small;
- that every fixed range the production code reads or writes lies inside its
  buffer.

Not proved: the keyed-hash (HMAC-SHA-256), SHA-256 and CRC algebra,
allocation and slice copying, walking variable-length index entries, parity
shard contents, Reed-Solomon recovery, and tape input and output.

### parity-capacity

Target: the terminal-close arithmetic in `crates/remanence-parity/src/capacity.rs`,
with small decision models of the progress and survivor selection in
`terminal_tail.rs` and `terminal_inventory.rs`. This is the arithmetic that
decides whether a tape still has room to finalize: to write its terminal
index, three replicas (A, B and C) separated by two separation extents.

The proofs cover:

- the replica payload size `64 × S + 256 × R` bytes for `S` structural
  entries and `R` object rows (this `S` is a count of entries, not the stripe
  count of the mapping above), with one header and one footer per replica;
- exactly three replica charges and two separation charges of one GiB each,
  at the three legal block sizes, with no record or filemark counted twice;
- the close reserve that object admission and manual finalization share, the
  pool watermark and capacity checks, the order of the tape and
  [spool](reference-glossary.md#spool) checks, and checked overflow;
- finalization progress through six states, one component at a time, with no
  progress after a failed [barrier](reference-glossary.md#barrier), no object
  admitted while finalizing, and a sealed tape only after replica C;
- choosing a surviving replica in the order C, B, A, reporting a conflict
  when valid survivors disagree, and falling back to a full scan from the
  beginning of the tape when none is valid.

Not proved: the encoding of the terminal index in CBOR (a compact binary data
format), the cryptographic and CRC algebra, and building the replica and
separation bytes. Nor are device positioning and filemarks, the order of
tape-log and catalog writes, the byte-level agreement check between replicas,
or the production code that gathers the inputs. The no-parity case is
extracted but has no dedicated theorem; the compiled behaviour comparison
covers it.

### pool-selection

Target: the ranking and admission kernels in
`crates/remanence-api/src/pool_selection.rs`, which choose the tape an object
is written to under the `complete-or-fill` and `fill-oldest` policies.

The proofs cover the fit and completion predicates, the leftover-space
arithmetic, each policy's ranking order and tie-breaks, and the admission
decision against the pool's low and high
[watermarks](reference-glossary.md#watermarks). An invalid watermark policy is
refused. A projected fill below the low watermark keeps the tape open, and a
fill between the watermarks admits the object and then finalizes the tape. An
overflow, a fill above the high watermark, or a close reserve that does not
fit means: finalize the current tape and retry.

Not proved: what happens on retry (finalizing the current tape, keeping the
object's identity and bytes, choosing another tape, and that retries end), the
catalog and drive projections that feed the ranking, and Rust's iterator and
collection code.

### rem-object-metadata

Target: the writer schema and validation arithmetic of the encrypted object's
metadata frame, in `crates/remanence-aead/src/metadata.rs`.

The proofs cover the conditions under which validation succeeds, and the
refusal of bad chunk and plaintext sizes and of arithmetic overflow. They
cover the exact four-key layout the writer emits and the round trip
decode(encode(x)) = x for a valid metadata core. The decoder is proved to
refuse wrong versions, digest algorithms, digest lengths and trailing data.

Not proved: copying the real digest bytes, skipping unknown CBOR extension
keys, encryption, hashing, or the byte-level round trip over production
values.

### rem-object-manifest

Target: the manifest writer schema and validation arithmetic in
`crates/remanence-format/src/layout.rs` and `manifest.rs`. The manifest is the
CBOR member index at the end of every object.

The proofs cover the chunk-count arithmetic and the writer's key layout for
the root and for a regular file. They prove round trips for three shapes:

- a manifest with one regular file;
- a fixed five-entry manifest: a file with one `user.` attribute, an empty
  file, a hard link, a symbolic link and a directory;
- the same five entries checked as an array, with duplicate paths and file
  ids refused and the hard-link target required to be an earlier regular
  file.

For manifests of any
length, they prove only progress: a sequence of steps that are each already
valid and duplicate-free reaches a final state. That result says nothing about
the final state, and duplicate refusal is proved only at the fixed size.

Not proved: production CBOR bytes, real strings and vectors, UTF-8, the tar
and pax layout, hashing, arbitrary attribute maps, the standard library's
`BTreeSet`, or `validate_manifest(encode_manifest(x))` over production values.

### tape-init

Target: `decide_tape_init` in `crates/remanence-api/src/tape_init.rs`, the
decision that `tape init` makes from what it read at the beginning of tape
(BOT), the catalog row and the label state.

The theorems check each case of the decision table, in the order production
tests them:

- committed copies in another or an unknown pool are an anomaly, before any
  other fact is considered;
- an unreadable, foreign or unrecognized BOT is refused;
- a blank tape is initialized only when its label is available and it has no
  committed copies;
- a clean Remanence bootstrap that matches its catalog row is a no-op;
- the hazards of a Remanence bootstrap produce their outcomes in order: label
  assigned elsewhere or retired, missing or mismatched catalog row, data past
  the bootstrap, committed copies, geometry mismatch, and a catalog row
  already written.

They are point checks of enumerated cases, not one theorem quantified over the
whole table.

Not proved: reading BOT, projecting the catalog, writing the bootstrap, or
the hardware steps around them.

### Limits shared by the schema proofs

In the metadata and manifest proofs, the schema numbers (map lengths, version
values, digest lengths, entry counts) are proved equal to the extraction's own
constants, not to independent literals. If a constant had been extracted
wrongly, the round trip would still succeed. The drift guards, which pin the
production constants, are what tie those numbers to production.

## What is not proved

These parts of Remanence have no formal proof. Rust unit and integration
tests, review, and test runs against a virtual tape library and a physical
library cover them ([tested hardware](status.md#tested-hardware)).

- SCSI, drive and changer control, and every physical tape operation.
- The daemon's sessions, cancellation, concurrency and gRPC interface.
- The catalog's persistence and its rebuild from the tape logs.
- REM-OBJECT's header, key frame and prefix geometry, and how a whole object
  is composed, beyond the metadata and manifest pieces above.
- Building and parsing sidecar bytes beyond the fixed layout above.
- The byte codecs of the terminal replicas and separation extents, the
  physical finalization sequence, end-of-data positioning, the byte-level
  agreement between replicas, and the recovery walk from BOT.
- The security of the encryption and of keyed authentication.

Earlier proofs of the previous encrypted representation's framing, header and
archive composition were removed in July 2026, when that representation was
replaced. Their drift guards no longer matched production, and keeping them
would have overstated what is proved. `verif/STATUS.md` records the planned
replacement proofs for the current header, key frame and range geometry.

## Running the inventory gate

The gate checks every area in one run:

```sh
make proof-inventory
```

It runs `verif/check-inventory.sh`, which needs `cargo`, `lake` and `rg` on the
path (it adds `$HOME/.elan/bin`). It does the following:

1. Regenerates the Lean for parity-capacity, parity-sidecar-layout and
   pool-selection with Charon and Aeneas, and compares it byte for byte with
   the checked-in files (`verif/check-generated-lean.sh`).
2. For every crate under `verif/`, confirms that a test named `drift_guard`
   exists, runs `cargo test drift_guard`, runs `cargo test`, and runs
   `lake build` in its `lean` directory.
3. Scans the project's Lean files, outside build caches, for `sorry`, `admit`
   and `axiom`.

Each step prints `PASS:` or `FAIL:` and its name. The summary line is
`PASS: checked 9 verification crates`, or `FAIL:` with the number of failed
checks and their names.

The Lean projects expect the Aeneas Lean library at
`../../../../toolchains/aeneas/backends/lean` relative to each
`verif/<area>/lean` directory, which is a `toolchains/aeneas` directory beside
the repository checkout. The regeneration step looks for Charon and Aeneas
under `$HOME/toolchains/aeneas` (`charon/bin/charon` and `bin/aeneas`); set
`AENEAS_ROOT`, `CHARON_BIN` or `AENEAS_BIN` to use another location. The
repository does not record which Aeneas revision the checked-in Lean was
generated with.

A drift guard alone needs only Cargo. To run one area's guard:

```sh
cd verif/parity-mapping
cargo test drift_guard
```

## Citing a proof

A code comment or document that refers to one of these proofs names the
kernel and the area, for example: "This arithmetic kernel has a Lean proof in
`verif/parity-mapping`; see `docs/formal-verification-status.md` and
`verif/parity-mapping/SPEC.md` for its scope." A statement that the code is
formally proved correct overclaims: each proof covers one kernel of an
extraction, within the boundaries listed above.
